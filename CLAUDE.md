# CLAUDE.md — Site StudioB04

Site vitrine statique et bilingue de StudioB04 : React 19 + TypeScript, React Router, Tailwind 4, design system `@studio_b04/ds` (^0.1.11). Pages pré-générées au build (SSG) puis hydratées. `README.md` décrit le projet ; ce fichier donne les règles pour y travailler.

## Règles du projet (décidées par le propriétaire)

- **Aucune bibliothèque externe sauf absolue nécessité.** Dépendances actuelles : `react`, `react-dom`, `react-router`, `@studio_b04/ds` ; en développement : Vite, `@vitejs/plugin-react`, TypeScript, Tailwind (`tailwindcss`, `@tailwindcss/vite`), Vitest, jsdom, Testing Library. N'en ajouter aucune sans accord. `clsx` est importé (`GlassBlock`, `MainLayout`, `MainNavigation`) sans être dans le `package.json` du site : il vient du design system, qui le déclare ; ne pas multiplier ces imports d'une dépendance transitive sans en parler.
- **React Router :** utiliser le paquet `react-router` (v8). `react-router-dom` n'est plus qu'une façade de la v7.
- **Langues :** français à la racine (`/`), anglais sous `/en/`, avec **une adresse traduite par langue** (`/mentions-legales/` et `/en/legal-notice/`, `/numerique/` et `/en/digital/`…) : le `slug` de chaque dossier de `src/pages` est dans les JSON, à côté des textes de la page. Pas de redirection selon la langue du navigateur. Seulement français et anglais.
- **Routes :** routage par dossiers (décision du propriétaire, à la manière de Next ou SvelteKit), sans liste à tenir : chaque fichier `src/pages/<Dossier>/<Dossier>.tsx` (il porte le nom de son dossier et exporte un composant par défaut) est une page, trouvée par Vite (`import.meta.glob`, dans `src/router/routes/pageModules.ts`), et `Router.tsx` en génère les `<Route>` pour chaque langue. Le chemin des dossiers, en camelCase et séparé par des points, est l'identifiant de la page et la clé de ses textes (`Print/Global/Global.tsx` → `print.global` → `pages.print.global`). `Home/Home.tsx` est l'accueil (`/` et `/en/`) ; le dossier `Error` est réservé (page d'erreur, sans adresse). Ne jamais écrire de `<Route>`, d'adresse (`path="legal-notice"`, `"/en/legal-notice/"`) ni de liste de pages à la main : une adresse vient de `getPath(pageId, locale)`. Les adresses inconnues tombent sur `<Route path="*">` (page 404). Six pages pour l'instant : `home`, `legal` et quatre pages provisoires (`web`, `print`, `enseignes`, `salons`, un simple `<div>`). Le bloc `pages.actu` des JSON n'a plus de dossier de page (`src/pages/Actu` a été retiré) : son adresse tombe sur la 404.
- **Textes :** toujours dans `src/i18n/locales/fr.json` et `en.json` (mêmes clés et mêmes `{{paramètres}}` ; un test le vérifie), jamais en dur dans les composants. Trois blocs : `site` (`site.name`, balises du `<head>`), `common` (textes partagés des layouts : `skiplinks.{header,main,footer}`, `main-menu.title`, `buttons.{scroll-to-top,back-to-home}`, `languageSwitcher`, `settings.{title,theme.{title,light,dark,system}}`) et `pages`. Sous `pages`, la clé d'une page est le chemin de ses dossiers en camelCase (`"home"`, `"legal"`, `"web"`, et `"global"` dans `"print"` pour `Print/Global`) ; le bloc d'une page a `title` et `description` (obligatoires, un test le vérifie), un `slug` quand l'adresse n'est pas le nom du dossier en kebab-case et un `link` (libellé du lien du menu principal) pour les pages du menu. Le bloc `pages.error` (`title` avec `{{status}}`, `intro`) est prévu pour les pages d'erreur. Les JSON ne gardent que les clés que le code lit : ne pas ajouter de clé qu'aucun code n'utilise, et retirer des deux langues celles qui ne servent plus (les anciens textes des pages retirées sont dans l'historique git). **Exception provisoire :** les pages `Home` et `Legal` n'affichent que du lorem ipsum (demande du propriétaire), et restent en dur le bouton « On s'apelle ? » et le libellé « Open main menu » de `MainNavigation`, ainsi que le texte de `SubFooter` (non affiché) ; à remplacer par des clés quand le contenu arrivera.
- **Lecture des textes :** `const { t } = useI18n();` puis `t("common.buttons.back-to-home")` (ou `t("la.cle", { status })` pour un texte `"… {{status}} …"`) ; hors React (balises du `<head>`), `translate(locale, key, params)`. `findMessage(locale, key)` renvoie `undefined` au lieu de la clé quand le texte n'existe pas : c'est ce qui lit le `slug` d'une page. Les paramètres s'écrivent `{{nom}}` dans le JSON. Les clés ne sont **plus typées** (`MessageKey` = `string`) : une clé fausse ou construite (``t(`pages.${page}.link`)``) n'est pas refusée à la compilation, elle s'affiche telle quelle dans la page. Après toute clé nouvelle ou renommée, vérifier qu'elle existe dans les deux JSON. `messages` donne le dictionnaire complet (pour une liste). Pas de bibliothèque d'internationalisation.
- **Navigation sans rechargement :** `MainLayout` est une route de layout unique (`<Outlet />`) : il reste monté d'une page à l'autre et au changement de langue (un test le vérifie). L'état global (par exemple un toast) peut y vivre ou dans `App.tsx`, au-dessus de `<Router />`.
- **Thème :** par défaut le site suit le réglage clair/sombre du système via les jetons du design system : tout est en CSS (`prefers-color-scheme` dans les jetons, le thème Tailwind pointe vers les mêmes jetons, donc pas de variante `dark:`). Depuis la demande du propriétaire, le dialog des réglages (`SettingsPanel`) permet de forcer clair ou sombre (voir « Thème : `useTheme()` » dans les conventions) : seul `src/theme` écrit `data-ds-theme`, jamais un composant.
- **Préprod = GitHub Pages**, déployée à chaque push sur `main` par `.github/workflows/deploy-preprod.yml` (typecheck + tests, puis build avec `VITE_NOINDEX=true`). Le site peut donc être servi sous un sous-dossier (`/Website/`) : voir « Sous-dossier d'hébergement » plus bas. Ne pas changer le déclencheur ni l'hébergement sans demande.
- **Tests unitaires** pour tout comportement ajouté ou modifié.
- Les documents, textes et échanges sont en français.

## Commandes

```bash
npm install
npm run dev          # Vite, http://localhost:5173 (réseau local inclus), sans pré-rendu
npm run build        # build:client + build:server + prerender → dist/client
npm run preview      # sert dist/client
npm run test:run     # Vitest, une exécution (npm test = mode watch)
npm run typecheck    # tsc --noEmit
```

Avant de livrer : `npm run typecheck && npm run test:run && npm run build`, puis `npm run preview` et vérifier dans le navigateur : aucune erreur console, navigation sans rechargement, page 404 sur une adresse inconnue. Si le changement touche aux liens, aux chemins ou aux ressources, refaire aussi le build en mode préprod (`BASE_PATH=/Website VITE_SITE_URL=https://studiob04.github.io/Website VITE_NOINDEX=true npm run build`, puis `BASE_PATH=/Website npm run preview`, sur http://localhost:4173/Website/).

## Architecture

- `index.html` : modèle du build, repères `<!--app-head-->` et `<!--app-html-->`. Il porte aussi les `<link>` de la police Red Hat Display (deux `preconnect` et la feuille Google Fonts) et `<meta name="color-scheme" content="light dark">`.
- `scripts/prerender.ts` : importe le module serveur, appelle `render(url)` pour chaque route de `getAllRoutes()`, écrit `dist/client/<chemin>/index.html`, plus `404.html`, `sitemap.xml`, `robots.txt`, puis supprime `dist/server`. En mode `NOINDEX` (préprod) : pas de `sitemap.xml`, et `robots.txt` sans `Disallow` ni ligne `Sitemap`. Exécuté par Node directement (TypeScript sans compilation).
- `src/entry/server.tsx` : `render(url)` = `prerender` de `react-dom/static` + `StaticRouter`, renvoie `{ html, head, locale }`. `build:server` le compile en `dist/server/server.js` (Vite nomme le fichier d'après l'entrée, sans le dossier) : `scripts/prerender.ts` lit ce chemin, donc déplacer ou renommer l'entrée impose de mettre à jour `package.json` et `prerender.ts`. Le `StaticRouter` reçoit `basename={BASE_URL}` et l'adresse préfixée par `BASE_URL`.
- `src/entry/client.tsx` (chargé par `index.html`) : `hydrateRoot` si la page contient déjà du HTML, sinon `createRoot` (cas du serveur de dev). `BrowserRouter` reçoit `basename={BASE_URL}`.
- `src/router/` (import `@/router`) : `routes/pageFiles.ts` contient les règles de découverte, sans Vite ni React : `parsePageFile`/`toPageFiles` (un chemin de fichier → page, identifiant, doublons refusés, accueil en premier), `resolveSlugs` (l'adresse : `slug` du JSON de chaque dossier, ou son nom en kebab-case, vide pour `home`). `routes/pageModules.ts` fait le `import.meta.glob` (eager, sans les tests ni `Error`) et expose `getPageModules()`, lue au premier appel et non à l'import. `routes/routes.ts` en dérive `getPages()` et `getPageIds()` (des `string` : l'identifiant d'une page n'est plus un type déduit des JSON, `PageId` n'existe plus et `mainNavPages`/`servicePages` non plus), `getSlug(pageId, locale)` (adresse traduite sans slash de bord, `imprimerie/global`, vide pour l'accueil), `getPath(pageId, locale)` (français sans préfixe, autres langues préfixées), `getAlternates`, `findPage`, `isCurrentPage(pageId, pathname)` (vraie pour la seule page affichée : la page mère d'une page imbriquée ne l'est pas, la 404 n'en a aucune ; le `pathname` se lit avec `useLocation()` dans le composant, la fonction ne lit ni `window` ni le contexte, pour rester valable au pré-rendu et se mettre à jour à la navigation ; sert à `aria-current="page"` sur le lien d'un menu), `getLocaleFromPath` et `getAllRoutes` (réservée au pré-rendu, au sitemap et aux tests). `index.ts` ré-exporte `routes.ts` et le composant `Router`. Le pré-rendu, le sitemap, `hreflang` et `findPage` passent par `getPath()` : une page nouvelle ou imbriquée n'y change rien.
- `src/router/Router/Router.tsx` : composant `Router` (export par défaut, ré-exporté par `@/router`). Rend `<Routes>` avec `<Route element={<MainLayout />}>` qui contient une route de layout sans adresse, `<Route element={<PageErrorBoundary />}>`, elle-même contenant `pages("fr")` sous `<Route path="/">`, `pages("en")` sous `<Route path="en">` et `<Route path="*" element={<ErrorPage status={404} />}>` pour la 404. `pages(locale)` génère à partir de `getPages()` un `<Route index>` pour l'accueil et une `<Route path={getSlug(id, locale)}>` par autre page (l'adresse peut avoir plusieurs niveaux : `imprimerie/global`) : une seule liste pour toutes les langues. Elle est appelée comme une fonction, pas comme un composant (un composant autour de `<Route>` est refusé par React Router). Il contient aussi `useDocumentUpdate` : à chaque navigation, met à jour `lang`, le titre et la description, remonte en haut de la page (`scrollTo({ top: 0 })`) et place le focus sur le `h1` de `#main` après un changement d'adresse (jamais au premier rendu).
- `src/App.tsx` : déduit la langue de l'adresse (`getLocaleFromPath`), la fournit à `I18nProvider`, enveloppe l'application dans `StudioB04Provider` (design system) et affiche `<Router />`. Il importe aussi `@/styles/global.css`. Rien d'autre : les routes sont dans `Router.tsx`.
- `src/head/index.ts` (import `@/head`) : `renderHead()` génère les balises SEO au build, **uniquement côté serveur** (jamais appelée dans le navigateur). React Router ne gère pas le `<head>`. Côté client, seuls `lang`, le titre et la description suivent la navigation (`useDocumentUpdate` dans `Router.tsx`, via `getPageMeta`) ; canonical, `hreflang`, Open Graph, `robots` et JSON-LD restent ceux de la page d'arrivée. Choix du propriétaire : le HTML pré-rendu de chaque adresse est correct, c'est ce que lisent les moteurs de recherche. Ne pas synchroniser le reste du `<head>` côté client sans demande. Ajoute `<meta name="robots" content="noindex">` sur la 404 et, si `NOINDEX`, sur toutes les pages.
- `src/config.ts` : `SITE_URL` (`VITE_SITE_URL`, défaut `https://www.studiob04.fr`, sous-dossier compris), `BASE_URL` (`import.meta.env.BASE_URL`, défini par `BASE_PATH` dans `vite.config.ts` : `/` ou `/Website/`) et `NOINDEX` (`VITE_NOINDEX === "true"`).
- `.github/workflows/deploy-preprod.yml` : push sur `main` → `npm ci`, `typecheck`, `test:run`, `build` avec `VITE_SITE_URL` et `BASE_PATH` issus de `actions/configure-pages` (`base_url`, `base_path`) et `VITE_NOINDEX=true`, puis publication de `dist/client` (`upload-pages-artifact` + `deploy-pages`).
- `src/layouts/` (import `@/layouts`, fichiers tenus par le propriétaire) : `MainLayout/MainLayout.tsx` est la route de layout, sans propriété. Il rend trois liens d'évitement (`SkipLink` de `@studio_b04/ds/uikit`, textes `common.skiplinks.*`, ancres `#header`, `#main`, `#footer` : chaque ancre doit viser un `id` existant, un test le vérifie), puis `div.main-layout` avec `<header id="header" role="banner">` (le composant `Header`), `<main id="main">` (l'`<Outlet />` et le bouton « retour en haut ») et `<footer id="footer" role="contentinfo">` (le composant `Footer`). Les `id`, les repères et les trois balises appartiennent à `MainLayout`, pas aux composants `Header` et `Footer`. `MainLayout` écrit la hauteur des trois balises dans `--header-height`, `--main-height` et `--footer-height` (`setHTMLCustomProp` de `@studio_b04/ds/utils`), lues par les CSS. Le bouton « retour en haut » (`.main-layout__inner__top-button`) reçoit `--visible` quand `globalThis.scrollY > 400` ; l'écoute du `scroll` (passive) est arrêtée au démontage par un `AbortController` (`return () => ac.abort()`) ; `inert` le retire de la tabulation et de l'arbre d'accessibilité tant qu'il est caché. Chaque layout a son CSS à côté (`Header.css`, `Footer.css`, `MainNavigation.css`, `SubFooter.css`, `MainLayout.css`), importé par le composant. `Header` : logo (lien vers l'accueil, `getPath("home", locale)`) et `MainNavigation`. `MainNavigation` : le menu principal, `<nav>` nommée (`common.main-menu.title`) avec un lien par page de la liste `["web", "print", "enseignes", "salons"]` (libellé `pages.<page>.link`, `aria-current="page"` via `isCurrentPage(page, pathname)`) et un bouton ; à partir de `md` (`useWindowSize().isMd` du design system) le menu est étalé, en dessous il est dans un `Dialog` (`#modal-main-navigation`) ouvert par un bouton et fermé au choix d'une page. `Footer` : lien vers les mentions légales (`AppLink`, `pages.legal.link`). `SubFooter` existe encore (et écrit `--subfooter-height`) mais `MainLayout` ne l'affiche plus. Mise en page : `MainLayout.css` (la fenêtre défile ; en-tête collé et rétréci au défilement, fond de points en `::before` de `main`, voir « Pièges connus »). Le test est à côté (`MainLayout.test.tsx`). La langue (`I18nProvider`) vient de `App.tsx` ; `lang`, titre, description et focus sont gérés par `Router`.
- `src/pages/` : une page = un dossier `<Nom>/<Nom>.tsx`, imbriquable (voir « Routes ») ; pas d'`index.ts` à tenir. `Home` : un `h1 tabIndex={-1}` et du lorem ipsum, en dur. `Legal` : un `h1 tabIndex={-1}` (texte `pages.legal.heading`, distinct du `title` du `<head>` qui porte le suffixe « – StudioB04 »), la date de mise à jour et quatre sections en Markdown (`pages.legal.{brand,responsability,edition,hosting}`). `Web`, `Print`, `Enseignes`, `Salons` : un `<div>` provisoire. Le `h1` de chaque page doit porter `tabIndex={-1}` pour que `Router` puisse lui donner le focus après une navigation. `Error/Error.tsx` : composant `ErrorPage` (propriété `status` : `404` par défaut ou `500`), titre (`heading`) et texte (`intro`) lus dans `pages.notFound` ou `pages.serverError`, lien de retour à l'accueil (`getPath("home", locale)`, texte `common.buttons.back-to-home`) ; les JSON n'ont pour l'instant que le bloc `pages.error` : ces deux blocs sont à y ajouter (ou `Error.tsx` à faire lire `pages.error`), sinon la page affiche les clés ; il n'a pas d'adresse et `src/pages/index.ts` n'exporte que lui (`import { ErrorPage } from "@/pages"`). Le dossier s'appelle `Error` mais le composant `ErrorPage`, pour ne pas masquer l'`Error` global de JavaScript.
- `src/router/ErrorBoundary/ErrorBoundary.tsx` : `PageErrorBoundary`, route de layout placée **dans** `MainLayout` : une erreur de rendu d'une page affiche `ErrorPage status={500}` à la place de la page, sans perdre l'en-tête ni le pied de page. La limite est identifiée par l'adresse (`key={pathname}`) : elle se réinitialise donc à la navigation suivante. Les erreurs 500 n'existent que dans le navigateur (rien n'est pré-généré ; une erreur de rendu au pré-rendu fait échouer le build).
- `src/components/AppLink/AppLink.tsx` : `Link` du design system + `useHref` (href avec le sous-dossier) + `useLinkClickHandler` de React Router (navigation interne sans rechargement). `src/components/GlassBlock/` : bloc « verre dépoli » (`GlassBlock.tsx`, `GlassBlock.type.ts`, `GlassBlock.css`) ; `as?: ElementType` choisit la balise (`div` par défaut, ou un composant), `className` s'ajoute à `glass-block` et les autres propriétés HTML (`HTMLAttributes<HTMLDivElement>`) passent à l'élément. `src/components/` contient `AppLink`, `GlassBlock`, `LanguageSwitcher` (n'est plus affiché nulle part pour l'instant), `SettingsPanel`, `LanguageButton` et `ThemeSwitcher`. `SettingsPanel` (rendu par `MainLayout`) est le bouton fixe qui ouvre le `Dialog` (`id="options"`) des réglages ; ce dialog contient `LanguageButton` (un lien-bouton par autre langue, vers la même page : `findPage` + `getAlternates`, navigation interne comme `AppLink`) et `ThemeSwitcher` (trois boutons à `aria-pressed` : clair, sombre, système).

## Conventions de code

- TypeScript strict, `verbatimModuleSyntax` : utiliser `import type` pour les types.
- Dates affichées : `formatDate(locale, isoDate?)` de `@/i18n` (« Mardi 24 Novembre 2026 » en français, date du jour sans `isoDate`), jamais `toLocaleDateString()` sans locale (celle de Node au prérendu n'est pas celle du navigateur : texte différent à l'hydratation). Elle utilise l'API Temporal quand elle existe (navigateurs récents) et `Date` sinon (Node 22 au prérendu, Vitest) ; `ESNext.Temporal` figure dans le `lib` de `tsconfig.json` pour typer `Temporal`. Les tests de `formatDate.test.ts` simulent `Temporal` avec `vi.stubGlobal`.
- Thème : `useTheme()` de `@/theme` renvoie `{ theme, setTheme }` (`"light" | "dark" | "system"`). Il pose `data-ds-theme="light|dark"` sur `<html>` (le design system en déduit `color-scheme` et les couleurs `light-dark()`) et retire l'attribut pour `"system"` (réglage du navigateur) ; le choix est gardé dans `localStorage` (`THEME_STORAGE_KEY`). Le premier rendu vaut toujours `"system"`, comme le HTML pré-rendu (pas d'écart à l'hydratation) ; le choix mémorisé est lu juste après. Le script en ligne de `index.html` repose le thème avant le premier affichage (sinon la page clignote) : il lit la même clé, et `theme.test.ts` vérifie qu'ils restent d'accord.
- Un composant par dossier : `src/components/<Nom>/<Nom>.tsx` en `export default function`, puis une ligne dans `src/components/index.ts` : `export { default as <Nom> } from "./<Nom>/<Nom>";`. Les fichiers propres au composant (test, styles) vont dans son dossier. Même organisation pour les layouts (`src/layouts/<Nom>/<Nom>.tsx` et `src/layouts/index.ts`) ; les pages n'ont pas d'`index.ts` (`src/pages/<Nom>/<Nom>.tsx` suffit).
- Un module de plusieurs fichiers vit dans un dossier avec un `index.ts` : `src/router/` (`index.ts` ré-exporte `Router/Router.tsx`, `routes/routes.ts`), `src/head/` (le code est dans `index.ts`), `src/theme/` (idem), `src/i18n/` (`index.tsx`, `formatDate.ts` et `locales/`). On l'importe par le dossier (`@/router`, `@/head`, `@/i18n`), jamais par un fichier interne (`@/router/routes/routes`). Son test est à côté du fichier testé (`src/head/head.test.ts`, `src/router/routes/routes.test.ts`) et importe, comme le reste, par `@/…`.
- Imports : tout ce qui remonte dans l'arborescence passe par l'alias `@/` (`@/i18n`, `@/router`, `@/head`, `@/config`), jamais par `../../…`. Les composants, les layouts et les pages s'importent via leur fichier d'index : `import { AppLink } from "@/components";`, `import { MainLayout } from "@/layouts";`, `import { ErrorPage } from "@/pages";`. Les imports dans le même dossier restent relatifs (`./server` depuis `src/entry/server.test.tsx`). Exception : à l'intérieur de `src/components` et de `src/router`, importer un autre fichier du même module par chemin relatif (`../AppLink/AppLink`, `../routes/pageModules`, `../ErrorBoundary/ErrorBoundary`), jamais par l'index (risque de dépendance circulaire). `Router.tsx` importe pourtant `@/router` : le cycle est sans effet parce que ces imports ne servent qu'au rendu (dans `pages()` et `useDocumentUpdate`) ; ne pas y ajouter d'import utilisé à l'évaluation du module (constante de module, par exemple). Pour la même raison, `getPageModules()` et `getPages()` lisent les pages au premier appel et non à l'import : une page peut importer `@/router` (pour un lien) sans créer de cycle à l'évaluation.
- Alias d'import : `@/*` → `src/*`. Un alias se déclare une seule fois, dans `paths` de `tsconfig.json` ; Vite, Vitest et le pré-rendu le lisent grâce à `resolve.tsconfigPaths: true` dans `vite.config.ts` (ne pas ajouter de `resolve.alias`).
- Styles : pour les pages et les composants, classes Tailwind du thème du design system. Les layouts (tenus par le propriétaire) ont leur CSS dans un fichier à côté du composant (`Header/Header.css`), importé par lui ; ne pas en créer ailleurs sans demande. `src/styles/global.css` (fichier tenu par le propriétaire, ne pas le modifier sans demande) contient l'ordre des couches, les imports, la police (couche `fonts`), un bloc `:root` (`font-size`, fond `--ds-bg-tertiary`, défilement doux) et un bloc `#root` (conteneur nommé `screen`, au moins `100dvh`, `100dvw` au plus `1920px`, centré, `overflow-x: clip`) ; les styles de base (couleurs du `body`, anneau de focus) viennent du reset du design system. Pour un jeton sans classe : `bg-(--ds-bg-inverse)`, `text-(color:--ds-text-inverse)`.
- CSS d'un layout : un fichier CSS est compilé seul, donc `@apply` d'un utilitaire qui dépend du thème (`container`, `p-lg`, `text-brand`…) exige `@reference "@/styles/global.css";` en première ligne (sans lui, `@apply container` ne donne que `width: 100%`) ; les utilitaires qui n'en dépendent pas (`mx-auto`) marchent sans. `@reference` n'ajoute aucun CSS. Points de rupture du thème : `sm` 37,5 rem, `md` 61,25 rem, `lg` 75 rem, `xl` 112,5 rem (`@media screen and (width > 61.25rem)` + commentaire `/* md */`). `.vscode/settings.json` (suivi par git) règle `css.lint.unknownAtRules` sur `ignore` : VS Code ne signale plus `@apply` ni `@reference`.
- Accessibilité (priorité du projet) : repères de page, navigations nommées, `aria-current`, `lang` sur les liens de langue, anneau de focus visible (fourni par le reset du design system), focus géré après navigation.
- Tests : Vitest + Testing Library, à côté du code. Chercher par rôle et nom accessible, pas par classe CSS. Les textes attendus se lisent avec `translate(locale, key)` ou `dictionaries` (`@/i18n`), pas en dur : un test suit ainsi les fichiers de langue (il ne détecte pourtant pas une clé absente, affichée telle quelle des deux côtés : vérifier les JSON à la main). jsdom n'a pas `matchMedia`, que lit `useWindowSize` du design system (donc `MainNavigation`, donc tout rendu de `MainLayout`) : `src/setup-tests.ts` en pose un stub (aucune requête ne correspond, écran étroit) ; pour tester l'écran large, `vi.stubGlobal("matchMedia", …)` dans le test. Un comportement qui lit le défilement (`scrollY`, `scrollTo`, écoute de `scroll`) se teste avec `Object.defineProperty(window, "scrollY", { configurable: true, value })` puis `fireEvent.scroll(window)` (jsdom ne défile pas) ; remettre `scrollY` à 0 dans `afterEach`. Les tests de rendu serveur commencent par `// @vitest-environment node`. `config.ts` lit l'environnement à l'import : pour tester `VITE_NOINDEX` ou `BASE_URL`, utiliser `vi.stubEnv(…)`, `vi.resetModules()` puis un `import()` dynamique du module testé, et `vi.unstubAllEnvs()` + `vi.resetModules()` dans `afterEach`. `src/entry/client.test.tsx` suit ce schéma pour `entry/client.tsx`, qui démarre l'application dès son import : `react-dom/client` y est enveloppé par `vi.mock` pour savoir si `createRoot` ou `hydrateRoot` est appelé et relever les erreurs d'hydratation récupérables ; utiliser le `act` de `@testing-library/react` (celui de `react` affiche un avertissement).

## Sous-dossier d'hébergement

La préprod vit sous `https://studiob04.github.io/Website/` (sauf domaine personnalisé), donc rien ne doit supposer que le site est à la racine :

- Liens internes : uniquement `Link`/`NavLink` de React Router ou `AppLink`, avec un chemin issu de `getPath()`. Jamais de `<a href="/…">`, de `window.location` ou de chemin en dur : ils ignoreraient le sous-dossier. Seules les ancres (`#main`) sont libres.
- Ressources : images, polices et CSS passent par Vite (import ou `public/`), qui ajoute le `base`. Ne pas écrire `/chemin` en dur dans du CSS ou du JSX.
- `SITE_URL` contient déjà le sous-dossier (c'est `base_url` de `configure-pages`) ; les URL absolues (canonical, `hreflang`, sitemap) s'écrivent `SITE_URL + getPath(…)`, sans y ajouter `BASE_URL`.
- Le `basename` de React Router est `BASE_URL` avec son slash final, pour que le lien vers l'accueil soit `/Website/` et non `/Website`.
- Préprod : ne jamais ajouter de `Disallow` à `robots.txt` (le `noindex` ne serait plus lu) ni de sitemap.

## Pièges connus

- **Couches CSS :** garder la déclaration `@layer base, properties, theme, fonts, utilities, components;` en première ligne de `global.css`, les imports `@studio_b04/ds/styles` et `@studio_b04/ds/reset` dans `layer(base)`, et `tailwindcss` puis `@studio_b04/ds/tailwind-theme` dans `layer(theme)` ; sinon des règles hors couche écrasent les classes Tailwind (`p-3`, `m-0`…).
- **Police :** chargée par les `<link>` de `index.html`, jamais par un `@import` dans `global.css` : Tailwind insère les imports locaux, et un `@import` distant qui suit une règle fait échouer le build (« @import statements must precede all other statements »). `global.css` ne fait que nommer la famille (`--ds-font-family-sans`, couche `fonts`).
- **Thème Tailwind du design system :** il supprime la palette par défaut ; l'espacement est basé sur 0,5 rem (`p-3` = 1,5 rem). Les noms (`bg-primary`, `text-brand`, `border-primary`) n'existent qu'à partir de `@studio_b04/ds` 0.1.6. Avec un lockfile, un `^` ne monte pas tout seul : pour changer de version, `npm install @studio_b04/ds@latest` (le site est sur `^0.1.11`).
- **Icônes du design system :** depuis la 0.1.8, `Icon` écrit un `<svg>` en ligne : `iconStart`, `iconEnd` et `external` sur `Link` et `Button` s'affichent (les boutons de `MainNavigation` et le bouton « retour en haut » de `MainLayout` en utilisent). Jusqu'à la 0.1.7 c'était un `<use href="data:…">` bloqué par les navigateurs, et ~730 Ko par page pré-rendue : ne pas redescendre sous la 0.1.8. `Icon` embarque toute la bibliothèque Lucide : JavaScript ≈ 720 Ko (≈ 200 Ko en gzip).
- **Animations de `MainLayout.css` :** deux animations liées au défilement de la page (`animation-timeline: scroll(root block)`, dans un `@supports (animation-timeline: scroll())` : sans prise en charge, rien ne bouge). `shrink-header` rétrécit l'en-tête collé (`.main-layout__header`) sur `--main-layout-header-size-diff` pixels de défilement ; `parallax-dots` déplace et efface le fond de points (le `::before` de `main.main-layout__inner`, calque `position: sticky` dont la hauteur est en `cqh`) sur `--fade-distance` (350 px). Deux pièges : les `@keyframes` se placent à la racine du fichier (imbriqués dans une règle, Chrome les ignore) ; l'axe surveillé doit être `block` (`scroll(root block)`) : avec l'axe `inline`, rien ne bouge. C'est la fenêtre qui défile, pas une zone interne : un `overflow: auto` ou `scroll` sur `.main-layout` ou `main` ferait défiler cette zone à la place, et la timeline `root` ne suivrait plus rien (`overflow: clip`, déjà sur `main`, ne crée pas de zone défilante).
- **Fond du survol du menu principal (`MainNavigation.css`) :** le fond du lien survolé ou au focus clavier n'est plus sur le lien mais dans le `::after` de la liste (`.main-navigation__inner__list`), positionné par ancrage CSS : `anchor-name` sur le lien survolé (`:focus-visible` compris), à défaut sur le lien de la page affichée puis sur le premier lien (le fond se range là en s'effaçant), et `position-anchor`, `anchor()` et `anchor-size()` sur le `::after`. Il glisse d'un lien à l'autre (`transition` sur `top`, `left`, `width`, `height`, durée `--ds-transition-delay-regular`, donc sans animation quand le visiteur réduit les animations). Le `::before` de chaque lien déborde de la moitié de l'espace entre les liens (`--main-navigation-gap`) pour qu'aucune zone morte ne fasse disparaître le fond d'un lien à l'autre ; cliquer dans cet espace active donc le lien voisin. L'ancre est la boîte transformée du lien (`scale` et `rotate` du survol compris) : ne pas remettre de `scale` sur le `::after`. Sans support de l'ancrage (`@supports not (anchor-name: …)`), le fond revient sur le lien lui-même. Pas de test automatisé possible (jsdom ne calcule pas le positionnement) : vérifier dans Chromium.
- **`StrictMode` (développement) :** les effets s'exécutent deux fois. Ne pas détecter le « premier rendu » avec un booléen : `useDocumentUpdate` (dans `Router.tsx`) compare l'adresse précédente (un test le couvre).
- **Rendu serveur :** ne pas lire `window` ni `document` pendant le rendu, seulement dans les effets.
- **Adresses :** une adresse ne doit jamais commencer par un code de langue (conflit avec le préfixe `/en/`) ni être celle d'une autre page de la même langue ; des tests le vérifient.
- **Ajouter une page :** créer `src/pages/<Nom>/<Nom>.tsx` (rien d'autre côté code : ni `<Route>`, ni enum, ni export), puis dans chaque JSON un bloc `pages.<nom>` avec `title` et `description` (le `<head>`), `heading` si le `h1` affiché diffère du `title` (sans le suffixe de marque : `Legal`), et `slug` si l'adresse n'est pas le nom du dossier en kebab-case (`TradeShows` → `trade-shows`) ; pour l'ajouter au menu, son identifiant dans la liste de `MainNavigation.tsx` et un `link` dans les deux JSON. Le `h1` de la page porte `tabIndex={-1}` (focus après navigation). Un test échoue si le bloc manque ; le test « renders $path » (une entrée par adresse de `getAllRoutes()`) couvre la page.
- **Pages imbriquées :** `Print/Global/Global.tsx` → bloc `pages.print.global`, adresse = `slug` de `print` puis `slug` de `global` (`/imprimerie/global/`, `/en/print/global/`). Un dossier sans page à lui seul (`Print/` sans `Print.tsx`) n'a que son `slug` dans `pages.print` et n'est pas une adresse (404).
- **Identifiants de page = `string` :** `"home"`, `"legal"`, `"print.global"`… ne sont plus un type déduit des JSON (`PageId` a été retiré de `@/router`, de même que le typage des clés de texte). TypeScript n'attrape donc plus ni une faute de frappe (`getPath("lgal", locale)`) ni une page sans bloc JSON : seuls les tests le font. Ne pas importer `PageId`, qui n'existe plus : un identifiant se type `string`. Un bloc JSON avec `title` et `description` sans dossier de page correspondant (comme `pages.actu`) n'est pas détecté : ne pas en laisser.
- **Noms de dossiers :** PascalCase, avec une seule casse par dossier (sur Mac `Print` et `print` sont le même dossier) et sans sigle en majuscules (`Faq`, pas `FAQ`, sinon la clé serait `fAQ`).
- **Autres fichiers de `src/pages` :** tout `.tsx` hors tests est embarqué dans le build même s'il n'est pas une page ; mettre les composants partagés dans `src/components`.
- **Serveur de dev :** n'injecte pas les balises SEO du `<head>` ; vérifier le SEO avec `build` + `preview`.
- **Lien d'évitement :** `SkipLink` vient du design system (`@studio_b04/ds/uikit`) ; il n'y a plus de version locale. Un lien dont l'ancre ne correspond à aucun `id` ne mène nulle part : les `id` (`header`, `main`, `footer`) sont posés par `MainLayout` lui-même, à côté des `SkipLink` ; en changer un impose de changer l'ancre (le test « points every link to exactly one element » échoue sinon).
- **Pages d'erreur :** les textes sont lus dans `pages.notFound` et `pages.serverError` (voir « Architecture ») : un texte absent du JSON s'affiche comme sa clé, y compris dans le `<title>` et la description de la 404 (`getPageMeta("notFound", …)`). La 404 est `ErrorPage status={404}` (route `*`) et `404.html` est générée en français uniquement (`render("/404/")`). La 500 (`PageErrorBoundary`) n'est jamais pré-générée. Le rendu client d'une adresse inconnue sous `/en/` se fait en anglais : mesuré dans Chrome : sous `/en/` le HTML français de `404.html` ne correspond pas au rendu anglais, React signale l'erreur #418 (écart d'hydratation) puis refait le rendu côté client ; le résultat affiché est correct (anglais). Sous la racine, aucune erreur. À corriger avant de rendre la 404 bilingue.
