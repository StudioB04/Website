# CLAUDE.md — Site StudioB04

Site vitrine statique et bilingue de StudioB04 : React 19 + TypeScript, React Router, Tailwind 4, design system `@studio_b04/ds` (≥ 0.1.8). Pages pré-générées au build (SSG) puis hydratées. `README.md` décrit le projet ; ce fichier donne les règles pour y travailler.

## Règles du projet (décidées par le propriétaire)

- **Aucune bibliothèque externe sauf absolue nécessité.** Dépendances actuelles : `react`, `react-dom`, `react-router`, `@studio_b04/ds` ; en développement : Vite, `@vitejs/plugin-react`, TypeScript, Tailwind (`tailwindcss`, `@tailwindcss/vite`), Vitest, jsdom, Testing Library. N'en ajouter aucune sans accord.
- **React Router :** utiliser le paquet `react-router` (v8). `react-router-dom` n'est plus qu'une façade de la v7.
- **Langues :** français à la racine (`/`), anglais sous `/en/`, avec **une adresse traduite par langue** (`/mentions-legales/` et `/en/legal-notice/`) : le `slug` de chaque dossier de `src/pages` est dans les JSON, à côté des textes de la page. Pas de redirection selon la langue du navigateur. Seulement français et anglais.
- **Routes :** routage par dossiers (décision du propriétaire, à la manière de Next ou SvelteKit), sans liste à tenir : chaque fichier `src/pages/<Dossier>/<Dossier>.tsx` (il porte le nom de son dossier et exporte un composant par défaut) est une page, trouvée par Vite (`import.meta.glob`, dans `src/router/routes/pageModules.ts`), et `Router.tsx` en génère les `<Route>` pour chaque langue. Le chemin des dossiers, en camelCase et séparé par des points, est l'identifiant de la page et la clé de ses textes (`Print/Global/Global.tsx` → `print.global` → `pages.print.global`). `Home/Home.tsx` est l'accueil (`/` et `/en/`) ; le dossier `Error` est réservé (page d'erreur, sans adresse). Ne jamais écrire de `<Route>`, d'adresse (`path="legal-notice"`, `"/en/legal-notice/"`) ni de liste de pages à la main : une adresse vient de `getPath(pageId, locale)`. Les adresses inconnues tombent sur `<Route path="*">` (page 404). Il n'y a pour l'instant que deux pages, `home` et `legal` ; les autres ont été retirées par le propriétaire, leurs textes restent dans les JSON.
- **Textes :** toujours dans `src/i18n/locales/fr.json` et `en.json` (mêmes clés), jamais en dur dans les composants. Sous `pages`, la clé d'une page est le chemin de ses dossiers en camelCase (`"home"`, `"legal"`, et `"global"` dans `"print"` pour `Print/Global`) ; le bloc d'une page a `title` et `description` (obligatoires, un test le vérifie) et un `slug` quand l'adresse n'est pas le nom du dossier en kebab-case ; `notFound` et `serverError` sont les textes des pages d'erreur (404 et 500). Les JSON ne gardent que les clés que le code lit : ne pas ajouter de clé qu'aucun code n'utilise, et retirer des deux langues celles qui ne servent plus (les anciens textes des pages retirées sont dans l'historique git). Hors de `pages`, il n'y a que `site.name` (balises du `<head>`) et `common.languageSwitcher` (composant `LanguageSwitcher`, non affiché pour l'instant). **Exception provisoire :** les pages `Home` et `Legal` n'affichent que du lorem ipsum écrit en dur (demande du propriétaire), de même que les libellés des liens d'évitement de `MainLayout`, le bouton du `Header` et le texte du `SubFooter` ; à remplacer par des clés quand le contenu arrivera.
- **Lecture des textes :** `const { t } = useI18n();` puis `t("pages.notFound.heading")` (ou `t("la.cle", { year })` pour un texte `"… {{year}} …"` : aucun texte n'a de paramètre pour l'instant) ; hors React (balises du `<head>`), `translate(locale, key, params)`. Les paramètres s'écrivent `{{nom}}` dans le JSON. Les clés sont typées (`MessageKey`) : une clé construite (``t(`pages.${key}.heading`)`` dans `ErrorPage`) doit rester un type de clé valide. `messages` n'est lu que pour les listes (aucune pour l'instant). Pas de bibliothèque d'internationalisation.
- **Navigation sans rechargement :** `MainLayout` est une route de layout unique (`<Outlet />`) : il reste monté d'une page à l'autre et au changement de langue (un test le vérifie). L'état global (par exemple un toast) peut y vivre ou dans `App.tsx`, au-dessus de `<Router />`.
- **Thème :** pas de bouton de changement de thème (demande abandonnée). Le site suit le réglage clair/sombre du système via les jetons du design system : tout est en CSS (`prefers-color-scheme` dans les jetons, le thème Tailwind pointe vers les mêmes jetons, donc pas de variante `dark:`), et le site n'écrit jamais `data-ds-theme`. Ne pas en ajouter sans demande.
- **Préprod = GitHub Pages**, déployée à chaque push sur `main` par `.github/workflows/deploy-preprod.yml` (typecheck + tests, puis build avec `VITE_NOINDEX=true`). Le site peut donc être servi sous un sous-dossier (`/Website/`) : voir « Sous-dossier d'hébergement » plus bas. Ne pas changer le déclencheur ni l'hébergement sans demande.
- **Tests unitaires** pour tout comportement ajouté ou modifié.
- Les documents, textes et échanges sont en français.

## Commandes

```bash
npm install
npm run dev          # Vite, http://localhost:5173 (réseau local inclus), sans pré-rendu
npm run build        # build:client + build:server + prerender → dist/client
npm run preview      # sert dist/client
npm run test:run     # Vitest, une exécution (npm test = mode watch)
npm run typecheck    # tsc --noEmit
```

Avant de livrer : `npm run typecheck && npm run test:run && npm run build`, puis `npm run preview` et vérifier dans le navigateur : aucune erreur console, navigation sans rechargement, page 404 sur une adresse inconnue. Si le changement touche aux liens, aux chemins ou aux ressources, refaire aussi le build en mode préprod (`BASE_PATH=/Website VITE_SITE_URL=https://studiob04.github.io/Website VITE_NOINDEX=true npm run build`, puis `BASE_PATH=/Website npm run preview`, sur http://localhost:4173/Website/).

## Architecture

- `index.html` : modèle du build, repères `<!--app-head-->` et `<!--app-html-->`. Il porte aussi les `<link>` de la police Red Hat Display (deux `preconnect` et la feuille Google Fonts) et `<meta name="color-scheme" content="light dark">`.
- `scripts/prerender.ts` : importe le module serveur, appelle `render(url)` pour chaque route de `getAllRoutes()`, écrit `dist/client/<chemin>/index.html`, plus `404.html`, `sitemap.xml`, `robots.txt`, puis supprime `dist/server`. En mode `NOINDEX` (préprod) : pas de `sitemap.xml`, et `robots.txt` sans `Disallow` ni ligne `Sitemap`. Exécuté par Node directement (TypeScript sans compilation).
- `src/entry/server.tsx` : `render(url)` = `prerender` de `react-dom/static` + `StaticRouter`, renvoie `{ html, head, locale }`. `build:server` le compile en `dist/server/server.js` (Vite nomme le fichier d'après l'entrée, sans le dossier) : `scripts/prerender.ts` lit ce chemin, donc déplacer ou renommer l'entrée impose de mettre à jour `package.json` et `prerender.ts`. Le `StaticRouter` reçoit `basename={BASE_URL}` et l'adresse préfixée par `BASE_URL`.
- `src/entry/client.tsx` (chargé par `index.html`) : `hydrateRoot` si la page contient déjà du HTML, sinon `createRoot` (cas du serveur de dev). `BrowserRouter` reçoit `basename={BASE_URL}`.
- `src/router/` (import `@/router`) : `routes/pageFiles.ts` contient les règles de découverte, sans Vite ni React : `parsePageFile`/`toPageFiles` (un chemin de fichier → page, identifiant, doublons refusés, accueil en premier), `resolveSlugs` (l'adresse : `slug` du JSON de chaque dossier, ou son nom en kebab-case, vide pour `home`). `routes/pageModules.ts` fait le `import.meta.glob` (eager, sans les tests ni `Error`) et expose `getPageModules()`, lue au premier appel et non à l'import. `routes/routes.ts` en dérive `PageId` (union des chemins de `pages` qui ont un `title` et une `description`, déduite des JSON, `notFound` exclu), `getPages()`, `getPageIds()`, `mainNavPages`, `servicePages`, `getSlug(pageId, locale)` (adresse traduite sans slash de bord, `imprimerie/global`, vide pour l'accueil), `getPath(pageId, locale)` (français sans préfixe, autres langues préfixées), `getAlternates`, `findPage`, `isCurrentPage(pageId, pathname)` (vraie pour la seule page affichée : la page mère d'une page imbriquée ne l'est pas, la 404 n'en a aucune ; le `pathname` se lit avec `useLocation()` dans le composant, la fonction ne lit ni `window` ni le contexte, pour rester valable au pré-rendu et se mettre à jour à la navigation ; sert à `aria-current="page"` sur le lien d'un menu), `getLocaleFromPath` et `getAllRoutes` (réservée au pré-rendu, au sitemap et aux tests). `index.ts` ré-exporte `routes.ts` et le composant `Router`. Le pré-rendu, le sitemap, `hreflang` et `findPage` passent par `getPath()` : une page nouvelle ou imbriquée n'y change rien.
- `src/router/Router/Router.tsx` : composant `Router` (export par défaut, ré-exporté par `@/router`). Rend `<Routes>` avec `<Route element={<MainLayout />}>` qui contient une route de layout sans adresse, `<Route element={<PageErrorBoundary />}>`, elle-même contenant `pages("fr")` sous `<Route path="/">`, `pages("en")` sous `<Route path="en">` et `<Route path="*" element={<ErrorPage status={404} />}>` pour la 404. `pages(locale)` génère à partir de `getPages()` un `<Route index>` pour l'accueil et une `<Route path={getSlug(id, locale)}>` par autre page (l'adresse peut avoir plusieurs niveaux : `imprimerie/global`) : une seule liste pour toutes les langues. Elle est appelée comme une fonction, pas comme un composant (un composant autour de `<Route>` est refusé par React Router). Il contient aussi `useDocumentUpdate` : à chaque navigation, met à jour `lang`, le titre et la description, et place le focus sur le `h1` après un changement d'adresse (jamais au premier rendu).
- `src/App.tsx` : déduit la langue de l'adresse (`getLocaleFromPath`), la fournit à `I18nProvider` et affiche `<Router />`. Rien d'autre : les routes sont dans `Router.tsx`.
- `src/head/index.ts` (import `@/head`) : `renderHead()` génère les balises SEO au build, **uniquement côté serveur** (jamais appelée dans le navigateur). React Router ne gère pas le `<head>`. Côté client, seuls `lang`, le titre et la description suivent la navigation (`useDocumentUpdate` dans `Router.tsx`, via `getPageMeta`) ; canonical, `hreflang`, Open Graph, `robots` et JSON-LD restent ceux de la page d'arrivée. Choix du propriétaire : le HTML pré-rendu de chaque adresse est correct, c'est ce que lisent les moteurs de recherche. Ne pas synchroniser le reste du `<head>` côté client sans demande. Ajoute `<meta name="robots" content="noindex">` sur la 404 et, si `NOINDEX`, sur toutes les pages.
- `src/config.ts` : `SITE_URL` (`VITE_SITE_URL`, défaut `https://www.studiob04.fr`, sous-dossier compris), `BASE_URL` (`import.meta.env.BASE_URL`, défini par `BASE_PATH` dans `vite.config.ts` : `/` ou `/Website/`) et `NOINDEX` (`VITE_NOINDEX === "true"`).
- `.github/workflows/deploy-preprod.yml` : push sur `main` → `npm ci`, `typecheck`, `test:run`, `build` avec `VITE_SITE_URL` et `BASE_PATH` issus de `actions/configure-pages` (`base_url`, `base_path`) et `VITE_NOINDEX=true`, puis publication de `dist/client` (`upload-pages-artifact` + `deploy-pages`).
- `src/layouts/` (import `@/layouts`, fichiers tenus par le propriétaire) : `MainLayout/MainLayout.tsx` est la route de layout, sans propriété. Il rend les liens d'évitement (`SkipLink` de `@studio_b04/ds/uikit`, libellés anglais en dur, ancres `#header`, `#main`, `#footer`, `#subfooter` : chaque ancre doit viser un `id` existant, un test le vérifie), `Header`, une zone centrale `.global-layout__inner` qui contient `<main id="main">` (l'`<Outlet />`) puis `Footer`, et `SubFooter`. Chaque layout a son CSS à côté (`Header.css`, `Footer.css`, `SubFooter.css`, `MainLayout.css`), importé par le composant. `Header` : logo (lien vers l'accueil, `getPath("home", locale)`), `<nav>` encore vide et bouton avec icône ; `Header`, `Footer` et `SubFooter` écrivent leur hauteur dans `--header-height`, `--footer-height` et `--subfooter-height` (`setHTMLCustomProp` de `@studio_b04/ds/utils`). Mise en page : `MainLayout.css` (grille sur `100dvh` ; la zone centrale est le seul élément qui défile ; fond de points en `::before` qui s'efface au défilement, voir « Pièges connus »). Le test est à côté (`MainLayout.test.tsx`). La langue (`I18nProvider`) vient de `App.tsx` ; `lang`, titre, description et focus sont gérés par `Router`.
- `src/pages/` : une page = un dossier `<Nom>/<Nom>.tsx`, imbriquable (voir « Routes ») ; pas d'`index.ts` à tenir. `Home` et `Legal` : un `h1 tabIndex={-1}` et du lorem ipsum, en dur. `Error/Error.tsx` : composant `ErrorPage` (propriété `status` : `404` par défaut ou `500`), titre, texte et lien de retour à l'accueil (`getPath("home", locale)`) lus dans `pages.notFound` ou `pages.serverError` ; il n'a pas d'adresse et `src/pages/index.ts` n'exporte que lui (`import { ErrorPage } from "@/pages"`). Le dossier s'appelle `Error` mais le composant `ErrorPage`, pour ne pas masquer l'`Error` global de JavaScript.
- `src/router/ErrorBoundary/ErrorBoundary.tsx` : `PageErrorBoundary`, route de layout placée **dans** `MainLayout` : une erreur de rendu d'une page affiche `ErrorPage status={500}` à la place de la page, sans perdre l'en-tête ni le pied de page. La limite est identifiée par l'adresse (`key={pathname}`) : elle se réinitialise donc à la navigation suivante. Les erreurs 500 n'existent que dans le navigateur (rien n'est pré-généré ; une erreur de rendu au pré-rendu fait échouer le build).
- `src/components/AppLink/AppLink.tsx` : `Link` du design system + `useHref` (href avec le sous-dossier) + `useLinkClickHandler` de React Router (navigation interne sans rechargement). `src/components/` ne contient plus que `AppLink` et `LanguageSwitcher` (ce dernier n'est plus affiché nulle part pour l'instant).

## Conventions de code

- TypeScript strict, `verbatimModuleSyntax` : utiliser `import type` pour les types.
- Un composant par dossier : `src/components/<Nom>/<Nom>.tsx` en `export default function`, puis une ligne dans `src/components/index.ts` : `export { default as <Nom> } from "./<Nom>/<Nom>";`. Les fichiers propres au composant (test, styles) vont dans son dossier. Même organisation pour les layouts (`src/layouts/<Nom>/<Nom>.tsx` et `src/layouts/index.ts`) ; les pages n'ont pas d'`index.ts` (`src/pages/<Nom>/<Nom>.tsx` suffit).
- Un module de plusieurs fichiers vit dans un dossier avec un `index.ts` : `src/router/` (`index.ts` ré-exporte `Router/Router.tsx`, `routes/routes.ts`), `src/head/` (le code est dans `index.ts`), `src/i18n/` (`index.tsx` et `locales/`). On l'importe par le dossier (`@/router`, `@/head`, `@/i18n`), jamais par un fichier interne (`@/router/routes/routes`). Son test est à côté du fichier testé (`src/head/head.test.ts`, `src/router/routes/routes.test.ts`) et importe, comme le reste, par `@/…`.
- Imports : tout ce qui remonte dans l'arborescence passe par l'alias `@/` (`@/i18n`, `@/router`, `@/head`, `@/config`), jamais par `../../…`. Les composants, les layouts et les pages s'importent via leur fichier d'index : `import { AppLink } from "@/components";`, `import { MainLayout } from "@/layouts";`, `import { ErrorPage } from "@/pages";`. Les imports dans le même dossier restent relatifs (`./server` depuis `src/entry/server.test.tsx`). Exception : à l'intérieur de `src/components` et de `src/router`, importer un autre fichier du même module par chemin relatif (`../AppLink/AppLink`, `../routes/pageModules`, `../ErrorBoundary/ErrorBoundary`), jamais par l'index (risque de dépendance circulaire). `Router.tsx` importe pourtant `@/router` : le cycle est sans effet parce que ces imports ne servent qu'au rendu (dans `pages()` et `useDocumentUpdate`) ; ne pas y ajouter d'import utilisé à l'évaluation du module (constante de module, par exemple). Pour la même raison, `getPageModules()` et `getPages()` lisent les pages au premier appel et non à l'import : une page peut importer `@/router` (pour un lien) sans créer de cycle à l'évaluation.
- Alias d'import : `@/*` → `src/*`. Un alias se déclare une seule fois, dans `paths` de `tsconfig.json` ; Vite, Vitest et le pré-rendu le lisent grâce à `resolve.tsconfigPaths: true` dans `vite.config.ts` (ne pas ajouter de `resolve.alias`).
- Styles : pour les pages et les composants, classes Tailwind du thème du design system. Les layouts (tenus par le propriétaire) ont leur CSS dans un fichier à côté du composant (`Header/Header.css`), importé par lui ; ne pas en créer ailleurs sans demande. `src/styles/global.css` (fichier tenu par le propriétaire, ne pas le modifier sans demande) contient l'ordre des couches, les imports, la police (couche `fonts`) et un bloc `:root` (page à `100dvh` × `100dvw`, conteneur nommé `screen`) ; les styles de base (couleurs du `body`, anneau de focus) viennent du reset du design system. Pour un jeton sans classe : `bg-(--ds-bg-inverse)`, `text-(color:--ds-text-inverse)`.
- CSS d'un layout : un fichier CSS est compilé seul, donc `@apply` d'un utilitaire qui dépend du thème (`container`, `p-lg`, `text-brand`…) exige `@reference "@/styles/global.css";` en première ligne (sans lui, `@apply container` ne donne que `width: 100%`) ; les utilitaires qui n'en dépendent pas (`mx-auto`) marchent sans. `@reference` n'ajoute aucun CSS. Points de rupture du thème : `sm` 37,5 rem, `md` 61,25 rem, `lg` 75 rem, `xl` 112,5 rem (`@media screen and (width > 61.25rem)` + commentaire `/* md */`). `.vscode/settings.json` (suivi par git) règle `css.lint.unknownAtRules` sur `ignore` : VS Code ne signale plus `@apply` ni `@reference`.
- Accessibilité (priorité du projet) : repères de page, navigations nommées, `aria-current`, `lang` sur les liens de langue, anneau de focus visible (fourni par le reset du design system), focus géré après navigation.
- Tests : Vitest + Testing Library, à côté du code. Chercher par rôle et nom accessible, pas par classe CSS. Les tests de rendu serveur commencent par `// @vitest-environment node`. `config.ts` lit l'environnement à l'import : pour tester `VITE_NOINDEX` ou `BASE_URL`, utiliser `vi.stubEnv(…)`, `vi.resetModules()` puis un `import()` dynamique du module testé, et `vi.unstubAllEnvs()` + `vi.resetModules()` dans `afterEach`. `src/entry/client.test.tsx` suit ce schéma pour `entry/client.tsx`, qui démarre l'application dès son import : `react-dom/client` y est enveloppé par `vi.mock` pour savoir si `createRoot` ou `hydrateRoot` est appelé et relever les erreurs d'hydratation récupérables ; utiliser le `act` de `@testing-library/react` (celui de `react` affiche un avertissement).

## Sous-dossier d'hébergement

La préprod vit sous `https://studiob04.github.io/Website/` (sauf domaine personnalisé), donc rien ne doit supposer que le site est à la racine :

- Liens internes : uniquement `Link`/`NavLink` de React Router ou `AppLink`, avec un chemin issu de `getPath()`. Jamais de `<a href="/…">`, de `window.location` ou de chemin en dur : ils ignoreraient le sous-dossier. Seules les ancres (`#main`) sont libres.
- Ressources : images, polices et CSS passent par Vite (import ou `public/`), qui ajoute le `base`. Ne pas écrire `/chemin` en dur dans du CSS ou du JSX.
- `SITE_URL` contient déjà le sous-dossier (c'est `base_url` de `configure-pages`) ; les URL absolues (canonical, `hreflang`, sitemap) s'écrivent `SITE_URL + getPath(…)`, sans y ajouter `BASE_URL`.
- Le `basename` de React Router est `BASE_URL` avec son slash final, pour que le lien vers l'accueil soit `/Website/` et non `/Website`.
- Préprod : ne jamais ajouter de `Disallow` à `robots.txt` (le `noindex` ne serait plus lu) ni de sitemap.

## Pièges connus

- **Couches CSS :** garder la déclaration `@layer base, properties, theme, fonts, utilities, components;` en première ligne de `global.css`, les imports `@studio_b04/ds/styles` et `@studio_b04/ds/reset` dans `layer(base)`, et `tailwindcss` puis `@studio_b04/ds/tailwind-theme` dans `layer(theme)` ; sinon des règles hors couche écrasent les classes Tailwind (`p-3`, `m-0`…).
- **Police :** chargée par les `<link>` de `index.html`, jamais par un `@import` dans `global.css` : Tailwind insère les imports locaux, et un `@import` distant qui suit une règle fait échouer le build (« @import statements must precede all other statements »). `global.css` ne fait que nommer la famille (`--ds-font-family-sans`, couche `fonts`).
- **Thème Tailwind du design system :** il supprime la palette par défaut ; l'espacement est basé sur 0,5 rem (`p-3` = 1,5 rem). Les noms (`bg-primary`, `text-brand`, `border-primary`) n'existent qu'à partir de `@studio_b04/ds` 0.1.6. Avec un lockfile, un `^` ne monte pas tout seul : pour changer de version, `npm install @studio_b04/ds@latest` (le site est sur `^0.1.8`).
- **Icônes du design system :** depuis la 0.1.8, `Icon` écrit un `<svg>` en ligne : `iconStart`, `iconEnd` et `external` sur `Link` et `Button` s'affichent (le bouton du `Header` en utilise un). Jusqu'à la 0.1.7 c'était un `<use href="data:…">` bloqué par les navigateurs, et ~730 Ko par page pré-rendue : ne pas redescendre sous la 0.1.8. `Icon` embarque toute la bibliothèque Lucide : JavaScript ≈ 720 Ko (≈ 200 Ko en gzip).
- **Fond de points de `MainLayout.css` :** le `::before` de `.global-layout__inner` est un calque `position: sticky` (hauteur en `cqh`, donc `container-type: size` sur le conteneur) dont l'opacité tombe à 0 sur les 500 premiers pixels de défilement (`--fade-distance`). Trois pièges : les `@keyframes` se placent à la racine du fichier (imbriqués dans une règle, Chrome les ignore) ; l'animation lit la timeline nommée `--main-timeline` (`scroll-timeline` sur le conteneur, axe vertical par défaut) : avec `scroll(nearest inline)`, l'axe surveillé était l'horizontal et rien ne bougeait ; le tout est dans un `@supports (animation-timeline: scroll())`, sans lui les points restent visibles.
- **`StrictMode` (développement) :** les effets s'exécutent deux fois. Ne pas détecter le « premier rendu » avec un booléen : `useDocumentUpdate` (dans `Router.tsx`) compare l'adresse précédente (un test le couvre).
- **Rendu serveur :** ne pas lire `window` ni `document` pendant le rendu, seulement dans les effets.
- **Adresses :** une adresse ne doit jamais commencer par un code de langue (conflit avec le préfixe `/en/`) ni être celle d'une autre page de la même langue ; des tests le vérifient.
- **Ajouter une page :** créer `src/pages/<Nom>/<Nom>.tsx` (rien d'autre côté code : ni `<Route>`, ni enum, ni export), puis dans chaque JSON un bloc `pages.<nom>` avec `title` et `description`, et `slug` si l'adresse n'est pas le nom du dossier en kebab-case (`TradeShows` → `trade-shows`). Un test échoue si le bloc manque ; le test « renders $path » (une entrée par adresse de `getAllRoutes()`) couvre la page.
- **Pages imbriquées :** `Print/Global/Global.tsx` → bloc `pages.print.global`, adresse = `slug` de `print` puis `slug` de `global` (`/imprimerie/global/`, `/en/print/global/`). Un dossier sans page à lui seul (`Print/` sans `Print.tsx`) n'a que son `slug` dans `pages.print` et n'est pas une adresse (404).
- **`PageId` est déduit des JSON :** c'est l'union des chemins de `pages` qui ont un `title` et une `description` (`"home"`, `"legal"`, `"print.global"`…), `notFound` exclu. TypeScript refuse une faute de frappe (`getPath("lgal", locale)`) mais ne connaît pas les dossiers : une page sans bloc JSON est détectée par un test, pas à la compilation. Un bloc avec `title` et `description` sans dossier de page correspondant reste un `PageId` valide : ne pas en laisser.
- **Noms de dossiers :** PascalCase, avec une seule casse par dossier (sur Mac `Print` et `print` sont le même dossier) et sans sigle en majuscules (`Faq`, pas `FAQ`, sinon la clé serait `fAQ`).
- **Autres fichiers de `src/pages` :** tout `.tsx` hors tests est embarqué dans le build même s'il n'est pas une page ; mettre les composants partagés dans `src/components`.
- **Serveur de dev :** n'injecte pas les balises SEO du `<head>` ; vérifier le SEO avec `build` + `preview`.
- **Lien d'évitement :** `SkipLink` vient du design system (`@studio_b04/ds/uikit`) ; il n'y a plus de version locale. Un lien dont l'ancre ne correspond à aucun `id` ne mène nulle part : si un `id` change dans `Header`, `Footer` ou `SubFooter`, changer l'ancre dans `MainLayout` (le test « points every link to exactly one element » échoue sinon).
- **Pages d'erreur :** la 404 est `ErrorPage status={404}` (route `*`) et `404.html` est générée en français uniquement (`render("/404/")`). La 500 (`PageErrorBoundary`) n'est jamais pré-générée. Le rendu client d'une adresse inconnue sous `/en/` se fait en anglais : mesuré dans Chrome : sous `/en/` le HTML français de `404.html` ne correspond pas au rendu anglais, React signale l'erreur #418 (écart d'hydratation) puis refait le rendu côté client ; le résultat affiché est correct (anglais). Sous la racine, aucune erreur. À corriger avant de rendre la 404 bilingue.
